## 4. TK-72 闭合提案 · DEC-16 第 ②③ 档（紧凑高度模式）

> **本节是提案，不是已实现项。** 🔒 **D9 纪律**：未获批准前，桌面版**不得**隐藏任何核心操作；当前 `main/main.js:125` 只输出 `heightTier` 判定值，**无任何收纳行为**。

### 4.1 问题陈述（为什么现在必须闭合 TK-72）

DEC-16 定义了三档：

| 档 | 定义 | 现状 |
|---|---|---|
| ① | 工作区足够 → 1024×680 标准最小客户区 | ✅ 已实现 |
| ② | 工作区不足 → 自动进入紧凑高度模式 | 🚧 **只判定，不收纳** |
| ③ | 更低 → 进一步收纳舞台及辅助信息，**确保输入、结果、警告、复制操作可用** | 🚧 **只判定，不收纳** |

**触发条件（P4-BASELINE §3.1 已裁决）**：P4-A 只实现第 ① 档；②/③ 档的收纳清单属**业务/视觉口径**，须先经 TK-72 闭合。阈值按 `scaleFactor` 换算，**不写死 712**（TK-79）。

### 4.2 实测数据支撑（本轮 Electron 45.1.0 实机采集）

> 采集方式：Playwright `_electron` 驱动桌面版 → `setContentSize()` → `getContentBounds()` 回读 + `getBoundingClientRect()` 逐元素测量。
> 机器：Windows 11 build 26300，缩放 100%（`scaleFactor=1`），工作区 2560×1392。

#### 4.2.1 非客户区增量与客户区下限（**修正 E-3 的一个口径**）

| 测量项 | 实测值 | 说明 |
|---|---|---|
| `getContentSize(1440,900)` → 外框 | 1040×965 | 增量 **16×65** |
| `getContentSize(1024,680)` → 外框 | 1040×745 | 增量 **16×65** |
| `setContentSize(1024, 640)` → 客户区 | **1024×654** | ⚠️ **不遵守 `minHeight`**（654 < 680） |
| `setContentSize(1024, 620/600/560/500/400)` → 客户区 | 1024×**654**（下限） | 同上 |
| `setSize(1024, 640)` → 客户区 | **1024×680** ✅ | `setSize` 遵守下限 |
| `getMinimumSize()` | **[1040, 745]** | = 1024+16 / 680+65 → **外框口径**的最小值 |
| 原生菜单是否侵占客户区 | **否**（900→900，只是外框 +26） | 印证 P4-BASELINE §3.2 的 C-2 裁决 |

> → **处置建议**：把 `frameH` 的台账口径改为 `39 + 26 = 65`（**仅改台账，不改窗口行为**）—— 列入 TK-145。
> 🔴 **`setContentSize` 不遵守 `minHeight`** 这一条**再次实测确认**（E-13 的复核），TK-83 的结论「不得用 `setContentSize` 做下界保证」**继续有效**。

#### 4.4.2 分档判定阈值（**按 `scaleFactor` 换算，不写死 712** —— TK-79）

> 🔴 实测依据：**总非客户区增量 = 65 DIP @100%**（39 + 26 原生菜单）；`getMinimumSize()` = 1040×745（外框口径）。
> 因此「客户区 680」所需的工作区高度 = `680 + 65×sf`。

```
clientH  = window.getContentBounds().height          // 客户区（DEC-14 口径）
minH     = 680                                        // DEC-07 最小标准客户区
needH    = minH + Math.round(65 * sf)                // 撑住 680 客户区所需的工作区高度

if (workArea.height >= needH)              tier = 1   // 标准档
else if (clientH >= 560)                   tier = 2   // 紧凑高度（轻量收纳）
else                                        tier = 3   // 极低高度（重量收纳）
```

| 阈值 | 含义 | @100% 实测工作区高度 |
|---|---|---|
| `workArea.height ≥ 745` | **第①档**：标准最小客户区 1024×680 **放得下** | ≥ 745 |
| `560 ≤ clientH < 680` | **第②档**：客户区不足 680 → 紧凑高度 | 窗口总高 < 745 |
| `clientH < 560` | **第③档**：极低 → 重量收纳（舞台折叠） | 窗口总高 < 625 |

> ⚠️ **本档位判定必须改到主进程**（`main/main.js:125` 现在只按 `work.height` 与 `frameH` 判，**没有读 `clientH`**），且必须在 `resize` 事件上重新判定（当前**只在启动时算一次**）。
> 💡 **建议实现位置**：`main/main.js` 在 `mainWindow.on('resize')` 中重算 tier → 通过**既有** `executeJavaScript` 只读通道（与 `syncMenuState()` 同一模式，**不新增 IPC 通道**，🔒 SEC-07）把 tier 推给渲染层 → 渲染层 `desktop-ui.js` 按 tier 应用 `.layout[data-height-tier="compact|tight"]` 的 CSS 类。
