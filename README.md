# LED 大屏比例与视频画布换算工具

将 LED 屏幕的实际宽高换算为真实比例，并辅助计算视频画布尺寸、比例误差及等比适配方式。

本项目源于作者在实际工作中经常和 LED 大屏（异形、特长屏）视频制作中的需求有联系，每次都在实际比例和像素转换的痛苦中。

作者本人没有编程基础，也不是职业开发者 —— 在本项目中承担的是**产品负责人**角色：提出使用场景、定义需求与验收标准、决定开发范围、执行测试验收，并对最终发行授权。

代码实现由多个 AI 模型在 Tencent WorkBuddy 中**分阶段协作**完成，并非某一个模型一次性产出 —— 完整分工、迭代时序与质量保障方式见下文「项目开发历程与 AI 协作」。

希望把这个实际工作中用得上的小工具分享给有类似需求的人，也方便其他使用者查看、反馈和改进。

**当前版本：1.0.1** · **离线使用** · **零依赖**

## 工具能做什么

- 根据 LED 屏幕的物理宽高，计算真实宽高比与最简整数比。
- 按指定宽度、指定高度、常用分辨率或整数倍方式换算画布尺寸。
- 对比候选分辨率与目标比例的误差。
- 提示画面比例不一致时的裁切或留边方案。
- 复制换算结果与现场参数说明，方便交接给后期或现场技术人员。

## 使用方法

### 普通使用：下载单文件版

**下载工具：** [下载 led-ratio-tool.html](https://github.com/ZacWild/LED-ratio-Tool/raw/refs/heads/main/dist/led-ratio-tool.html)，保存到本地后使用浏览器打开即可。
如果没有发布版本，也可以在仓库的 `dist/` 目录中获取 `led-ratio-tool.html`。

1. 双击打开 HTML 文件，无需安装。
2. 输入 LED 屏幕的实际宽度和高度，并确认单位。
3. 选择目标比例与画布换算模式。
4. 查看分辨率和误差，使用「复制完整参数」整理交付信息。

工具在本地浏览器中计算，不需要联网，也不会主动上传输入的数据。

### 开发版

仓库中的 `index.html` 需要与 `src/` 目录一起使用。主要文件：

- `src/core.js`：比例与画布换算逻辑
- `src/app.js`：页面交互与结果展示
- `src/styles.css`：界面样式
- `dist/led-ratio-tool.html`：可独立运行的离线单文件版

## 重要说明

**屏幕物理尺寸不等于 LED 控制系统的原生像素分辨率。** 本工具根据输入尺寸计算比例和画布建议，不会推导控制器、播放服务器实际支持的分辨率。

正式交付前，请向现场技术方确认：

- LED 控制系统接收分辨率
- 后期合成分辨率
- 最终交付文件分辨率

不要仅凭工具计算结果判断现场设备一定能够播放；具体参数以控制系统、播放设备及现场技术方确认为准。

另外，行业俗称不一定等于严格数学比例。例如，严格的 **21:9 = 7:3 ≈ 2.3333:1**。请以实际尺寸计算出的比例为准，不要直接用俗称替代实测结果。

本项目**不是「一句话生成」的产物**。它是在项目负责人主导下，由多个 AI 模型分阶段协作实现，并依靠 Git 版本管理、自动化测试、CI 与人工验收逐步收敛的软件项目。

| 开发阶段 | 使用模型 | 工作范围 |
|---|---|---|
| P1–P3 | Space Bunny | 项目前期主体开发 |
| P4–P5 | Step5-preview | 功能完善、测试与 Preview 阶段 |
| P6 | MiniMax M3.1 Flash | Release Readiness、测试体系完善、缺陷修复、打包与 CI |
| RC 收尾及后续 | DeepSeek V4.1 | TK 遗留问题处理、局部修复、工程文档、PR 与发行准备 |

> 📌 **记录口径**
>
> - 阶段边界的划分依据是仓库内**可查证的工程记录**（`CHANGELOG.md`、`desktop/DESIGN-ALIGNMENT.md` 的 TK 台账、PR 提交历史），不凭印象归属；
> - 本表**只记录有对应产物与文档证据的参与**，不虚构模型未承担的任务；
> - 模型名称（`Space Bunny` / `Step5-preview` / `MiniMax M3.1 Flash` / `DeepSeek V4.1`）沿用引入时的写法，**不随后续版本迭代改写大小写或加简称**；
> - 同一阶段内的返工与缺陷修复计入该阶段模型，不再细拆到更小的模型粒度。

**分工原则**

| 角色 | 职责 |
|---|---|
| 项目负责人（人类） | 需求定义、产品决策、开发范围界定、测试验收、最终发行授权；涉及业务红线与视觉基准的变更须书面确认后方可执行 |
| AI 模型 | 在其所属阶段内完成代码实现、测试辅助与工程任务执行，并对该阶段产物负责；跨阶段的结论不互相背书 |

**质量保障链路**（每个阶段都需通过才算完成）

- **Git 与 PR**：功能开发在 `feature/desktop-windows` 分支进行，`main` 受规则集保护，合并需项目负责人授权。
- **自动化测试**：单元测试、业务红线守卫、桌面 E2E、200 组差分、视觉回归、高 DPI 验收等门禁，逐项条数与当前状态见 [`desktop/README.md`](desktop/README.md)。
- **CI**：GitHub Actions 在每次推送与 PR 时执行完整门禁（36 个步骤），其状态检查已纳入分支保护。
- **人工验收**：产品负责人对可用性、视觉与发行条件做最终判定 —— **自动化通过不等于可以发布**。

> Windows 桌面版（Electron）的开发过程、测试矩阵与发行状态记录在 [`desktop/README.md`](desktop/README.md)；
> 设计基线与逐条落地对照记录在 [`desktop/DESIGN-ALIGNMENT.md`](desktop/DESIGN-ALIGNMENT.md)。

## 开发与测试

项目不依赖第三方 npm 包。修改计算逻辑后，可运行测试：

```bash
node --test test/core.test.mjs
```

构建独立离线文件：

```bash
node build.mjs
```

修改前端代码后，请重新构建 `dist/led-ratio-tool.html`，避免单文件版仍保留旧内容。
